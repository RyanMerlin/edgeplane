EdgePlane's governance system lets you require human or automated sign-off before certain actions proceed inside a domain. An **approval request** carries the action being requested, an optional target entity, a reason, and context — forming a structured audit trail regardless of whether the request is granted or rejected.

## How It Works

Approval requests are scoped to a domain. Any agent, operator, or automated process can create a request; a separate authorized party then approves or rejects it. The requesting side waits (or polls) for a decision before proceeding.

The flow has three stages:

1. **Create** — the actor that wants to perform an action creates an approval request describing what it wants to do and why.
2. **Review** — an authorized reviewer lists pending requests and inspects them.
3. **Decide** — the reviewer approves or rejects the request, optionally with a note.

Policy events generated by these decisions are available for auditing through the admin surface.

## The Approvals CLI

### Create a Request

```sh
edgeplane approvals create \
  --domain-id <domain-id> \
  --action "publish-artifact" \
  --reason "Releasing v1.2.0 build artifact to the shared workspace" \
  --target-entity-type "artifact" \
  --target-entity-id "<artifact-id>" \
  --request-context '{"build_ref": "sha256:abc123", "triggered_by": "ci-agent"}' \
  --expires-in-seconds 3600
```

| Flag | Required | Description |
|------|----------|-------------|
| `--domain-id` | Yes | The domain this request is scoped to. |
| `--action` | Yes | A string naming the action being requested (e.g. `publish-artifact`, `create-task`, `deploy`). The format is defined by your domain's governance policy. |
| `--reason` | No | Human-readable explanation of why the action is needed. Shown to reviewers. |
| `--channel` | No | Notification channel name. If set, EdgePlane notifies that channel when the request is created. See [Channel Notifications](#channel-notifications). |
| `--target-entity-type` | No | The type of entity the action targets (e.g. `artifact`, `task`, `mission`). |
| `--target-entity-id` | No | The ID of the specific entity being acted on. |
| `--request-context` | No | Arbitrary JSON object with additional context (build refs, agent state, etc.). Stored and returned with the request. |
| `--expires-in-seconds` | No | If set, the request automatically expires after this many seconds if no decision is made. |

### List Pending Requests

```sh
edgeplane approvals list \
  --domain-id <domain-id> \
  --status pending \
  --limit 20
```

| Flag | Required | Description |
|------|----------|-------------|
| `--domain-id` | Yes | Filter to this domain. |
| `--status` | No | Filter by status: `pending`, `approved`, or `rejected`. Omit to return all. |
| `--limit` | No | Maximum number of results to return. |

### Approve a Request

```sh
edgeplane approvals approve \
  --approval-id <approval-id> \
  --note "Confirmed build hash matches expected artifact" \
  --expires-in-seconds 86400
```

| Flag | Required | Description |
|------|----------|-------------|
| `--approval-id` | Yes | The numeric ID of the approval request (from the `create` or `list` output). |
| `--note` | No | Optional reviewer note attached to the approval decision. |
| `--expires-in-seconds` | No | If set, the approval grant expires after this duration. Useful for time-bounded access or one-shot permissions. |

### Reject a Request

```sh
edgeplane approvals reject \
  --approval-id <approval-id> \
  --note "Artifact hash mismatch — re-trigger build before publishing"
```

| Flag | Required | Description |
|------|----------|-------------|
| `--approval-id` | Yes | The numeric ID of the approval request. |
| `--note` | No | Optional note explaining the rejection. Stored in the audit trail and visible to the requesting party. |

## Channel Notifications

The `--channel` flag on `approvals create` ties into EdgePlane's channel notification system. When a channel name is provided, EdgePlane notifies that channel when the approval request is created. This allows reviewers subscribed to that channel to be alerted in real time rather than polling the list.

Channel names are domain-configured. Refer to your domain's profile for the channels available in that context.

## Auditing Policy Events

Approval decisions emit governance policy events. These are queryable via the admin surface:

```sh
# Most recent 50 policy events (default)
edgeplane admin policy events

# Limit to the last 10
edgeplane admin policy events --limit 10
```

Each event records the action, the decision (approved/rejected), the reviewer identity, the timestamp, and any notes. This gives a complete audit log of every governance decision in the system.

The active policy and its version history are also available:

```sh
# Show the currently active governance policy
edgeplane admin policy active

# List previous policy versions
edgeplane admin policy versions --limit 20
```

## Common Patterns

### Gating Task Creation

An agent that needs to create a task inside a restricted domain can create an approval request first:

```sh
# Agent creates an approval request before opening a task
edgeplane approvals create \
  --domain-id <domain-id> \
  --action "create-task" \
  --reason "Spawning refactor subtask from parent mission analysis" \
  --target-entity-type "mission" \
  --target-entity-id "<mission-id>"

# Operator reviews and approves
edgeplane approvals list --domain-id <domain-id> --status pending
edgeplane approvals approve --approval-id <approval-id>

# Agent proceeds with task creation after observing approved status
```

### Gating Artifact Publish

Before publishing a build artifact to shared storage, a CI agent can request approval from a domain owner:

```sh
edgeplane approvals create \
  --domain-id <domain-id> \
  --action "publish-artifact" \
  --channel "releases" \
  --target-entity-type "artifact" \
  --target-entity-id "<artifact-id>" \
  --request-context '{"version": "2.1.0", "build_id": "<build-id>"}' \
  --expires-in-seconds 7200
```

If no decision arrives before `--expires-in-seconds` elapses, the request transitions to expired and the agent should retry or escalate.

### Human-in-the-Loop Workflows

For agent workstreams that should pause at defined checkpoints:

1. Agent completes a phase and creates an approval request with `--action "proceed-to-next-phase"` and `--reason` describing what was produced.
2. A human reviewer inspects the artifacts, then approves or rejects.
3. On approval, the agent resumes. On rejection, the agent reads the `--note` and revises.

This pattern keeps humans in control of phase boundaries without requiring them to monitor every agent action.

## Governance Policy Management

The governance policy defines which actions require approval, who can approve them, and what the default behavior is when no matching policy rule exists. Policies are managed as versioned JSON documents:

```sh
# Create a draft from a policy JSON file
edgeplane admin governance policy create-draft --file policy.json --change-note "Add artifact publish gate"

# Publish the draft
edgeplane admin governance policy publish --draft-id <draft-id> --change-note "Approved by domain owner"

# Roll back to a specific version if needed
edgeplane admin governance policy rollback --version 3 --change-note "Reverting to stable policy"

# Reload the active policy config on the server
edgeplane admin governance policy reload
```
